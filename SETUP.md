## First-time setup

The project is defined by `project.yml` and generated with XcodeGen. `HyroxCoach.xcodeproj` is not committed; regenerate it from the project root, `/Users/stanleyyoung/Challenge 4`.

Install XcodeGen with Homebrew:

```bash
brew install xcodegen
```

From the project root, generate the Xcode project:

```bash
xcodegen generate
```

Open the generated project:

```bash
open HyroxCoach.xcodeproj
```

The project contains two targets:

| Target | Platform | Bundle ID |
| --- | --- | --- |
| `HyroxCoach` | iOS 17+ | `com.stanleyyoung.HyroxCoach` |
| `HyroxCoachWatch` | watchOS 10+; modern single-target WKApplication style | `com.stanleyyoung.HyroxCoach.watchkitapp` |

The iOS app embeds the watch app. Source files are organised as follows:

- `HyroxCoach/` contains the iOS sources.
- `HyroxCoachWatch/` contains the watchOS sources.
- `Shared/` is compiled into both targets.

## Setting your Development Team

Both targets must be signed before Xcode can install them on real hardware. Every experiment in this project requires real hardware, so signing is needed even when you are only following the experiment steps. A free Apple ID is sufficient for development on your own devices; you do not need a paid Apple Developer Program membership for this project.

### Add your Apple ID to Xcode first

Before you can choose a team, add your Apple ID to Xcode:

1. Open Xcode and choose **Xcode → Settings → Accounts**.
2. Click **+**, choose **Apple ID**, and sign in.
3. Select the account you just added.

For a free account, the team appears as **Your Name (Personal Team)**, using your name in place of **Your Name**.

### Set the team on both targets

There are two targets in this project. This is the step most often half-completed: the signing settings are separate, so setting the team on one target does not set it on the other.

1. Open `HyroxCoach.xcodeproj`.
2. Select the project (the blue project icon) in the navigator, then select the `HyroxCoach` target.
3. Open the **Signing & Capabilities** tab.
4. Tick **Automatically manage signing**.
5. Choose your team from the **Team** dropdown.
6. Repeat steps 2–5 for the `HyroxCoachWatch` target.

Check both targets individually. The iOS target can build successfully while the watch target still has no team.

### Critical gotcha: XcodeGen overwrites UI signing changes

This project is generated by XcodeGen from `project.yml`. When you regenerate the project, XcodeGen overwrites `HyroxCoach.xcodeproj`, so any team selected only through the Xcode UI is lost the next time the project is regenerated.

The durable fix is to set `DEVELOPMENT_TEAM` in `project.yml`. It currently holds an empty string. The setting is:

```yaml
settings:
  DEVELOPMENT_TEAM: ABCDE12345
```

In this repository, the shared settings are currently nested under `settings: base:`. Keep that existing `base:` nesting and replace only the empty value, so the relevant part of `project.yml` becomes:

```yaml
settings:
  base:
    SWIFT_VERSION: "5.0"
    GENERATE_INFOPLIST_FILE: "NO"
    CODE_SIGN_STYLE: Automatic
    DEVELOPMENT_TEAM: ABCDE12345
```

Replace `ABCDE12345` with your own Team ID. Do not add a second `settings:` block. After editing `project.yml`, regenerate the project:

```bash
xcodegen generate
```

The shared setting is then applied to both targets automatically. If the project was open in Xcode, close and reopen the generated project after regeneration.

### Finding your Team ID

You can find the Team ID in more than one way:

- In Xcode, open **Xcode → Settings → Accounts**, select your team, and read the ID shown for it. You can also use the **Manage Certificates** sheet for that team.
- After signing at least once, run the following command:

```bash
security find-identity -v -p codesigning
```

  In the certificate name, the ten-character string in parentheses is the Team ID.
- After setting the team once in the Xcode UI, inspect the generated project:

```bash
grep -m1 DEVELOPMENT_TEAM HyroxCoach.xcodeproj/project.pbxproj
```

### Privacy

A Team ID is not a secret in the way an API key is, but it identifies your developer account. Since this repository is private, putting the Team ID in `project.yml` is acceptable. If the repository is ever made public, keep `DEVELOPMENT_TEAM` out of `project.yml` and pass it at build time instead, for example:

```bash
xcodegen generate && xcodebuild -project HyroxCoach.xcodeproj -scheme HyroxCoachWatch DEVELOPMENT_TEAM=ABCDE12345 build
```

### Verify the watch target is signed

Build the watch scheme for a generic physical watchOS platform:

```bash
xcodebuild -project HyroxCoach.xcodeproj -scheme HyroxCoachWatch -destination 'generic/platform=watchOS' build
```

A successful signed build for `generic/platform=watchOS`—not the Simulator—is the real proof that the team is set correctly on the watch target.

### Troubleshooting signing

#### “Signing for 'HyroxCoachWatch' requires a development team”

**Symptom:** Xcode shows “Signing for 'HyroxCoachWatch' requires a development team”.

**Cause:** The team is not set on the watch target specifically, even though the iOS target builds.

**Fix:** Set the team on `HyroxCoachWatch` in **Signing & Capabilities**, then set `DEVELOPMENT_TEAM` in `project.yml` and regenerate so the setting is durable.

#### “Failed to register bundle identifier”

**Symptom:** Xcode shows “Failed to register bundle identifier”.

**Cause:** The bundle ID is already taken by another Apple ID.

**Fix:** Change `PRODUCT_BUNDLE_IDENTIFIER` in `project.yml` to a unique value such as `com.<yourname>.HyroxCoach`. The watch app's ID must remain the iOS ID with `.watchkitapp` appended, for example `com.<yourname>.HyroxCoach.watchkitapp`. Regenerate the project after changing the IDs.

#### The app stops launching from the watch after seven days

**Symptom:** An app installed with a free Apple ID stops launching from the watch after several days.

**Cause:** Free Apple ID provisioning profiles expire after seven days.

**Fix:** Rebuild the app from Xcode with the iPhone and Apple Watch available so Xcode can provision it again.

#### The team resets to blank after regeneration

**Symptom:** The Team field is blank again after the generated project is regenerated.

**Cause:** `project.yml` was not updated; the team was changed only in the Xcode UI.

**Fix:** Set `DEVELOPMENT_TEAM` in `project.yml` as described in the critical gotcha subsection, then regenerate the project.

## Verify HealthKit on both targets

After generation, open **Signing & Capabilities** for each target in turn and confirm that **HealthKit** appears for both `HyroxCoach` and `HyroxCoachWatch`.

Both targets have the HealthKit capability through their `.entitlements` files. Both target Info.plists carry `NSHealthShareUsageDescription` and `NSHealthUpdateUsageDescription`. The capability and the usage descriptions are separate requirements.

If HealthKit is missing from either target, stop before running the app. Check that the target's entry in `project.yml` includes its `.entitlements` file and HealthKit capability, correct the source configuration, regenerate the project, and reopen it. Do not treat a hand-edited generated `.xcodeproj` as the source of truth. Verify the capability on both targets again after regeneration.

## Running on real hardware

HealthKit and the watch-to-phone connection must be tested on real hardware.

1. Pair the Apple Watch with the iPhone in the Watch app.
2. Connect the iPhone to the Mac and accept the **Trust This Computer** prompt. Complete any pairing or trust prompts shown for the watch.
3. In Xcode, select the watch scheme, `HyroxCoachWatch`, and choose the physical paired Apple Watch as the run destination.
4. Build and run the watch target. The iOS app embeds the watch app, so installation is coordinated through the phone.

The first watch-app installation can take a long time. Leave the process running, and keep the iPhone nearby during installation.

## Troubleshooting

### Crash immediately when requesting HealthKit authorisation

**Symptom:** The app crashes as soon as it requests HealthKit authorisation.

**Cause:** One of the target Info.plists is missing `NSHealthShareUsageDescription` or `NSHealthUpdateUsageDescription`.

This is a **runtime crash**, not a build error. It can therefore look like a code bug rather than a configuration mistake. Add both usage descriptions to the relevant target Info.plist, regenerate if the plist is defined through the project configuration, and check both targets.

### “Signing for ... requires a development team”

**Symptom:** Xcode reports “Signing for ... requires a development team”.

**Cause:** The team is not set on one of the two targets. Setting it on `HyroxCoach` does not set it on `HyroxCoachWatch`.

Set the Team for both targets in **Signing & Capabilities**, then record `DEVELOPMENT_TEAM` in `project.yml` so regeneration preserves it.

### The watch app does not appear on the watch

**Symptom:** The iOS app is installed, but the watch app does not appear on the paired Apple Watch.

**Cause:** The watch installation is pending or the watch-to-iOS bundle relationship is wrong.

Check the Watch app on the iPhone for a pending installation. Then check that `WKCompanionAppBundleIdentifier` in the watch Info.plist matches the iOS bundle ID exactly: `com.stanleyyoung.HyroxCoach`.

### Changes to `project.yml` do not take effect

**Symptom:** A change in `project.yml` is not visible in Xcode.

**Cause:** The generated Xcode project is stale.

Run XcodeGen again from `/Users/stanleyyoung/Challenge 4`, then reopen the generated project:

```bash
xcodegen generate
```

### Edits made in Xcode's project settings disappear

**Symptom:** A setting changed in Xcode is gone after regeneration.

**Cause:** XcodeGen overwrote the generated project with the values in `project.yml`.

Make the change in `project.yml` instead, then regenerate. Treat `project.yml` as the source of truth; changes made only in the generated `.xcodeproj` will not survive regeneration.

## Reading the experiment logs

Open **Console.app**, select the paired Apple Watch in the sidebar, and filter by the subsystem `com.stanleyyoung.HyroxCoach`.

The log timestamps are the actual experimental evidence for Cycle L1. Treat a gap in the ticks as the app being suspended. The logs survive suspension, which is what makes that gap visible after the fact.
